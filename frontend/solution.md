# Решение задачи: страница-заглушка с кнопкой в Telegram на своём VPS

## Вводные

- Раньше была одностраничная информационная страница на Tilda с кнопкой в телеграм-канал.
- Страницу удалили (сменили тариф) — нужно поднять аналог на своём VPS.
- Домен для заглушки: **beautyhelper.ru** (отдельный, не тот, что у существующего проекта).
- VPS уже арендован, на нём уже крутится один другой проект — значит, nginx и порты 80/443 могут быть уже заняты. Проверяем это на шаге 1.
- Полноценный фронтенд не нужен — только заглушка, чтобы сайт не висел.
- Нужен счётчик Яндекс.Метрики (счётчик уже создан).

## Что уже известно про проект

- nginx в репозитории нет.
- `docker/docker-compose.yaml` поднимает: `db` (5432), `redis` (6379), `rabbitmq` (5672 / 15672), `celery_worker`, `celery_beat`, `app` (uvicorn, 8000).
- Порты 80 и 443 никем из compose не заняты → статику будем отдавать через nginx рядом с проектом.

## Общий маршрут

Делаем строго по одному шагу, следующий — только после результата предыдущего.

1. Разведка VPS — что уже стоит, свободны ли порты, куда смотрит домен
2. Разбор существующего конфига nginx (установка не нужна — nginx уже есть)
3. HTML-страница с кнопкой
4. Конфиг nginx, проверка по http://
5. HTTPS через certbot (уже установлен)
6. Вставка счётчика Яндекс.Метрики

## Что приготовить заранее

Понадобится на шагах 3 и 6:

- ~~имя домена~~ → `beautyhelper.ru`
- ссылка на телеграм-канал (`https://t.me/...`)
- номер счётчика Яндекс.Метрики (число, видно в Метрике рядом с названием сайта)

## Шаг 1. Разведка

**Статус:** ✅ готово

Зайти на VPS по SSH и выполнить четыре команды, вывод сохранить/прислать.

```bash
# 1. Какая ОС
cat /etc/os-release | head -2

# 2. Стоит ли уже nginx
nginx -v 2>&1 || echo "nginx не установлен"

# 3. Кто занимает порты 80 и 443
sudo ss -tlnp | grep -E ':80 |:443 ' || echo "порты 80 и 443 свободны"

# 4. Публичный IP сервера
curl -s ifconfig.me; echo
```

Одна проверка **с локального компьютера** (не с VPS) — куда сейчас указывает домен:

```bash
dig +short твойдомен.ru
```

Если `dig` нет — подойдёт `nslookup твойдомен.ru`.

### Что мы проверяем

IP из команды 4 (на сервере) и IP из `dig` (локально) должны совпасть.

- **Совпали** → A-запись домена уже настроена на VPS, идём к шагу 2.
- **`dig` вернул пусто или чужой IP** (например, старый тильдовский) → сначала правим DNS у регистратора домена. Это будет отдельным шагом.

### Результаты (26.08.2026)

- ОС: Ubuntu 24.04.4 LTS
- nginx: **уже установлен**, версия 1.24.0 (Ubuntu)
- порты 80/443: **заняты этим же nginx** (pid 89481/89483)
- IP сервера: 155.212.138.80
- docker: не установлен, существующий проект — просто папка со статикой
- существующий сайт на сервере: `onemoreday.fun` (его не трогаем)
- наш домен: `beautyhelper.ru` — добавляем вторым независимым сайтом
- `dig` по домену: **SERVFAIL** — DNS-зона домена не отвечает (см. блокер ниже)
- вход на сервер: `ssh root@155.212.138.80`, по ключу `~/.ssh/id_ed25519`, без пароля

**Вывод:** ставить nginx не нужно. Добавляем второй сайт в уже работающий nginx,

Конфиг соседа **не трогаем**.

## ✅ Решённый блокер: DNS-зона домена оставалась у Tilda (26.08.2026)

**Статус:** решено

### Причина найдена

`whois beautyhelper.ru` на сервере:

```
nserver:   ns1.tildadns.com.
nserver:   ns2.tildadns.com.
state:     REGISTERED, DELEGATED, UNVERIFIED
created:   2025-01-04
paid-till: 2027-01-04
```

Домен зарегистрирован в Beget и оплачен до 04.01.2027 — с регистрацией всё в порядке.
Но **NS-серверы у него тильдовские**, то есть DNS-зону обслуживает Tilda, откуда мы ушли.
Тильдовские NS отвечают нестабильно → `SERVFAIL` у `dig`/`getent`.
Chrome при этом иногда показывает старую страницу — он ходит через свой DNS-over-HTTPS
и/или отдаёт закэшированное.

**Следствие:** панель Beget → «Редактировать DNS» сейчас ни на что не влияет —
интернет спрашивает записи не у Beget, а у Tilda.

### План починки

1. Сменить NS домена на `ns1.beget.com` / `ns2.beget.com` (в панели Beget, он же регистратор)
2. Подождать распространения — от 15 мин до суток
3. Прописать A-запись `beautyhelper.ru → 155.212.138.80` (и `www` туда же)
4. Проверить: `dig +tcp +short beautyhelper.ru` должен вернуть `155.212.138.80`

### ✅ Решено 26.08.2026

- почты на домене нет — переезд зоны безопасен
- в панели Beget нажата кнопка «Делегировать NS Beget» → делегирование осуществлено
- добавлены A-записи: `beautyhelper.ru` → `155.212.138.80` и `www.beautyhelper.ru` → `155.212.138.80`
- NS разошлись примерно за час: `whois` показывает `ns1.beget.com` и др.,
  `dig +tcp +short beautyhelper.ru` → `155.212.138.80` ✅

### Побочно: почему не работает `dig`

VPN (`tun0`, `DNS Domain: ~.`) забирает весь DNS на себя и режет UDP:53 к локальному
резолверу. Обход — флаг `+tcp`: `dig +tcp +short домен`.
Для сравнения: `onemoreday.fun` через `+tcp` резолвится нормально в `155.212.138.80`.

## Шаг 4. Конфиг nginx и проверка по http://

**Статус:** ✅ готово (26.08.2026)

- страница залита: `/var/www/beautyhelper/index.html` (через `scp` с локальной машины)
- конфиг: `/etc/nginx/sites-available/beautyhelper`, копия в репозитории —
  `frontend/nginx-beautyhelper.conf`
- включён симлинком в `sites-enabled`
- `nginx -t` → test is successful, применено через `systemctl reload nginx`
- проверка без DNS: `curl -s -H "Host: beautyhelper.ru" http://127.0.0.1/` отдаёт нашу страницу ✅

Пока только порт 80 — блок HTTPS допишет certbot на шаге 5.

**Грабли:** heredoc (`cat > файл <<'EOF'`) в терминале Вероники ломается — при вставке
добавляются отступы, а закрывающий `EOF` обязан стоять в начале строки без пробелов.
Решение: создавать файл локально и заливать через `scp`.

## Шаг 5. HTTPS через certbot

**Статус:** ✅ готово (26.08.2026)

```bash
certbot --nginx -d beautyhelper.ru -d www.beautyhelper.ru
```

- сертификат: `/etc/letsencrypt/live/beautyhelper.ru/fullchain.pem`
- действует до **24.11.2026**, автопродление настроено certbot'ом (таймер systemd)
- certbot сам дописал в `/etc/nginx/sites-available/beautyhelper` блок `listen 443 ssl`
  и редирект с http на https
- `https://beautyhelper.ru` и `https://www.beautyhelper.ru` открываются с замочком ✅

Проверить, что автопродление живо (вхолостую, ничего не меняет): `certbot renew --dry-run`
