# Beauty Helper — описание проекта и компетенций

**Тема:** разработка асинхронного веб-приложения с использованием искусственного интеллекта.

**Суть:** бэкенд-приложение принимает ссылку на косметическое средство, анализирует
состав через OpenAI API и возвращает PDF-отчёт с детальным разбором каждого компонента
и итоговым выводом. Только бэкенд, демонстрация через Swagger.

**Стек:** Python (asyncio), FastAPI, SQLAlchemy 2.0, PostgreSQL, Redis, RabbitMQ,
Celery, Docker, S3 (aioboto3), OpenAI SDK, ReportLab, JWT/bcrypt, Alembic, Ruff,
pytest, GitHub Actions.

## Покрываемые компетенции

Ниже — какие компетенции курса покрыты и чем именно (с указателями на код), чтобы
было видно, где что реализовано.

### Устройство языка
- **asyncio / async-await** как основа HTTP-слоя: FastAPI + `asyncpg`, асинхронные
  сессии SQLAlchemy (`core/database.py`, `core/repository/sqlalchemy.py`).
- **Стандартная и сторонние библиотеки**: OpenAI SDK, ReportLab (PDF), aioboto3 (S3),
  PyJWT, bcrypt, openpyxl, Celery/Kombu.
- **Идиомы языка**: dataclass-DTO (`apps/products/dto.py`), декораторы
  (`s3_safe_call` — ретраи с бэкоффом, `infrastructure/s3/decorators.py`),
  enum-статусы (`SelectionStatus`, `WaitingStatus`, `BalanceOperationType`),
  контекстные менеджеры для сессий.
- **Границы применимости языка**: осознанное разделение sync/async — там, где нужен
  блокирующий код (Celery-воркер с psycopg2 и sync-OpenAI), он изолирован от event loop.

### Web-программирование
- **REST API** на FastAPI: регистрация/логин/refresh/logout, пакеты, баланс,
  анализ продукта, «мои подборки» (см. таблицу эндпоинтов в README).
- **Проектирование эндпоинтов и сериализация**: Pydantic-схемы запросов/ответов,
  `response_model`, статусы подборки (created / pending / done / parsing / error).
- **Аутентификация/авторизация**: JWT (access + refresh), blacklist токенов в Redis,
  зависимость `get_current_user` (`core/security.py`).
- **Понимание устройства фреймворка**: dependency injection (`Depends`), lifespan,
  роутеры, автодокументация Swagger.

### High performance
- **Async I/O вместо блокирующих вызовов** на HTTP-слое: БД, выдача ответа не блокируют
  event loop; тяжёлая работа (OpenAI → PDF → S3) вынесена в **фоновые задачи Celery**,
  поэтому API отвечает быстро, не дожидаясь генерации.
- **Контроль внешних лимитов**: Limiter выбирает аккаунт OpenAI по RPM/TPM/IPM через
  счётчики в Redis, KeyManager ротирует ключи — защита от упора в rate-limit.
- **Надёжность под нагрузкой**: идемпотентность задач (Redis-lock на `selection_id`,
  `retry`, `acks_late`), модель резерва круток с блокировкой строки (`SELECT FOR UPDATE`)
  — защита от гонок и потери оплаченных генераций.
- *Профилирование и бенчмарки sync vs async — возможное развитие, в текущей версии
  не выполнялись.*

### Software engineering
- **Чистая модульная архитектура**: паттерн **Repository → Service**, оркестратор
  как точка сборки флоу; отдельные async/sync реализации репозиториев.
- **Инфраструктура**: Docker + docker-compose (PostgreSQL, Redis, RabbitMQ, app,
  Celery worker, Celery beat), миграции Alembic, сидинг пакетов и демо-данных на старте.
- **Тесты**: 37 тестов — unit (баланс, лимитер, разбивка состава, PDF-оркестрация,
  безопасность) и интеграционные (оркестратор на реальной тестовой БД, 4 ветки флоу
  с моками OpenAI/S3/Celery).
- **Качество и поддержка**: Ruff (линт+формат), pre-commit-хуки, CI на GitHub Actions
  (ruff + pytest), централизованное логирование, обработка ошибок внешних сервисов
  с ретраями.
- **Проектирование архитектуры**: явная граница sync/async, изоляция транзакций и
  подключений между FastAPI (asyncpg) и Celery (psycopg2).

### Анализ данных
Прямой задачи анализа датасетов с визуализацией в проекте нет — это не его профиль.
Косвенно затронуто: структурирование «сырых» данных состава, расчёт стоимости запросов
(токены → USD/RUB), агрегация ответов OpenAI в итоговый отчёт. Визуализация/датасеты —
возможное развитие, в фокус текущей работы не входили.
